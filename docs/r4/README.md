## Contract status

R4 is selected. It rebuilds Lintel's logged-in product as a serious light engineering verification workstation. R4A locks the engineer workflow, reference responsibilities, visual-system documentation tokens, Workspace shell ownership, product-truth boundaries, accessibility and performance requirements, and the handoff to R4B and R4C. It does not reopen strategy and does not authorize production implementation.

The application opens into work requiring judgment, not generic analytics. The governing evidence model is:

`Change → Observation → Evidence → Requirement → Human Decision`

The governing authority model is:

- Lintel recommends.
- The accountable engineer decides.
- A recommendation and a Human Decision are separate records. They are never described, styled, counted, or communicated as equivalent outputs.

## Target engineer and working context

The primary user is the engineer accountable for deciding whether a pull request is ready to merge: commonly a senior reviewer, staff or principal engineer, reliability or security reviewer, or an engineer carrying service ownership. They work through an interrupt-driven queue, compare analysis runs, inspect technical evidence, and need to leave a defensible decision tied to the relevant change.

The Workspace optimises for repeated review over sustained desktop sessions. It must remain useful under dense records, partial data, low confidence, missing commit identity, and unresolved requirements. It is not a management dashboard, line-comment bot, CI replacement, policy enforcement console, free-form graph, or generic AI chat surface.

## First five seconds

Within five seconds of opening a selected review, an engineer must understand all of the following without opening a modal or changing mode:

1. which repository and pull request are selected;
2. the change title and current run or commit identity when available;
3. Lintel's recommendation and the risk band or score;
4. the highest-impact reason the review is not ready, or the strongest ready signal;
5. the count of open and blocking requirements;
6. whether evidence or proof is missing;
7. whether the current Human Decision is pending, applicable, stale, withdrawn, or unavailable;
8. the next inspection target or next accountable action.

If any fact is unavailable, the interface states that limitation in place. It never substitutes fixture, inferred, previous-run, or recommendation-derived data without an explicit label.

## Canonical workflow

The binding review workflow is:

1. Open a review needing attention.
2. Understand Lintel's recommendation and risk.
3. Identify the highest-impact finding.
4. Inspect its supporting evidence.
5. Understand missing proof.
6. Inspect affected files, surfaces, or focused diff context that current data truthfully supports.
7. Inspect the resulting requirements.
8. Resolve or reopen canonical merge conditions where the current persistence contract permits it; acknowledge or accept risk only through an explicit supported Human Decision contract. Do not invent a general requirement waiver.
9. Compare the current analysis run with the previous run.
10. Understand recommendation, risk, finding, evidence, and requirement movement.
11. Determine whether the review is ready for an accountable decision.
12. Record the Human Decision.
13. Preserve the decision against the applicable run and commit when available, or require explicit acknowledgement of an unbound decision.
14. Communicate the current result through the truthful GitHub workflow: use the implemented configured GitHub App comment path where available; otherwise expose only the documented blueprint/export boundary.

## R4 acceptance standard

R4 is acceptable only when the logged-in application is recognisably one light engineering system; the selected review dominates the experience; the full evidence chain is inspectable; recommendation, risk, missing proof, requirements, run movement, staleness, and Human Decision remain semantically distinct; every consequential action is deliberate and accessible; capability and provenance labels are truthful; large collections remain usable; and the functional narrow and mobile flows preserve the same review responsibility.

R4A acceptance locks these contracts only. No production implementation begins before the R4C visual laboratory is accepted. After R4C acceptance, the accepted laboratory becomes production's visual authority and the external reference products cease governing production decisions.
